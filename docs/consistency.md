# Consistency

One HTTP Stream Load request is one atomic Doris batch. Daft may invoke the sink for multiple micropartitions, and one micropartition may be split into multiple physical requests by row or serialized-byte limits.

The connector therefore does not provide all-or-nothing DataFrame writes. A network failure after request transmission is an ambiguous write. The connector raises an ambiguous-write error and never replays the payload automatically under another label.

Transport failures are classified by request phase. A connection failure before the request body reaches the socket is a non-ambiguous `DorisWriteError`; response loss, truncated/malformed/oversized response bodies, invalid response counters, and timeout/connection errors with an unknown server result after body transmission are generally `DorisAmbiguousWriteError`. A malformed response carrying an HTTP 4xx status is a known client-side rejection and is reported as `DorisWriteError`; HTTP 5xx and status-less malformed responses remain ambiguous. An explicit Doris `Fail` or `Label Already Exists` response remains a known-result error. Neither class performs an automatic replay. Stream Load redirect handling is a protocol hand-off, not a retry with a new label, and a redirected request that fails after transmission is also classified by the same response-status rule.

`Success` means Doris accepted the load. `Publish Timeout` means the load transaction completed but publication may be delayed; it is not a retry signal. The first release does not enable Doris Stream Load 2PC and does not claim exactly-once behavior under native task retry. Doris writes are rejected before metadata access under the Ray runner, so the first release does not expose a Ray side-effect retry path whose duplicate behavior would be hidden behind this contract.
